Arquitectura UML 4+1

Modelamos Sockbuster con el paradigma 4+1 de Kruchten: cuatro vistas que muestran el sistema desde distintos ángulos (lógica, desarrollo, procesos y física) y una quinta vista de escenarios que las conecta. Todos los diagramas están hechos en PlantUML y usan los mismos nombres de clases y componentes que el código del sitio.

Diagrama de Clases

Vista Lógica

Representa las entidades del dominio de Sockbuster y cómo se relacionan. Dejamos Calcetin al centro porque es la clase con más relaciones: pertenece a una Coleccion (agregación, porque la colección agrupa modelos que pueden existir por sí solos), está inspirado en una Tematica que guarda si es película o serie, recibe Resenas y aparece en los ItemCarrito.

La compra se lee por la izquierda. Un Usuario arma uno o más Carritos, cada carrito contiene sus ítems (composición: si se borra el carrito, se borran sus ítems) y al confirmar genera como máximo un Pedido con su EstadoPedido. El Rol del usuario (CLIENTE o ADMIN) es el dato que después viaja dentro del token JWT.

Diagrama de Componentes

Vista de Desarrollo

Muestra cómo está organizado el código en capas. Arriba están las páginas, hechas con HTML5, Tailwind CSS (compilado a un solo archivo) y JavaScript sin frameworks. Todas las llamadas pasan por el ApiGateway, que es el único punto de entrada: busca la ruta, valida la firma y el vencimiento del JWT y, si la ruta es de administración, exige el rol ADMIN (si no, responde 401 o 403).

Debajo hay un servicio por cada área del negocio y cada uno usa solo su propia colección de datos (patrón base de datos por servicio). Así AuthService no comparte los datos de usuarios con el catálogo, lo que ayuda al RNF02. En el prototipo las bases son arreglos de datos.js guardados en localStorage y la pasarela de pago es simulada. Como las páginas solo conocen el gateway, cada servicio podría pasar a un servidor real sin cambiar el HTML.

Diagramas de Secuencia y de Actividad

Vista de Procesos

Checkout. Es el proceso más delicado, porque dos clientes pueden querer el último par al mismo tiempo. PedidoService hace en paralelo (bloque par) la reserva de stock y el cálculo del total. La reserva es una sección crítica: en el código se encola con una promesa (colaReservas) para que se atienda de a una. Si falta stock se responde 409 y no se llama a la pasarela. Si la pasarela rechaza el pago, el pedido queda RECHAZADO y el stock se libera con un mensaje asíncrono.

Filtrado. Cuando el cliente cambia un filtro, la página espera 250 ms sin cambios (debounce) para no consultar por cada letra. CatalogoService busca los calcetines de la colección y calcula el promedio de estrellas al mismo tiempo (fork, que en el código es un Promise.all), y después filtra por talla, precio y texto y ordena el resultado.

Diagrama de Despliegue

Vista Física

El sitio que entregamos es estático y está publicado en GitHub Pages, que lo sirve por HTTPS desde su CDN. Con eso cumplimos el RNF01: no hay servidor que mantener y la carga inicial son pocos archivos livianos (el CSS ya va compilado y las fotos de los calcetines son SVG que se dibujan en el navegador, así que no hay imágenes pesadas).

El resto del diagrama es la infraestructura que proponemos para producción: un balanceador NGINX con TLS 1.3 que reparte las peticiones entre dos servidores Node.js en Docker (si uno se cae, el otro sigue atendiendo), una base PostgreSQL primaria con una réplica y los datos cifrados con AES-256 en reposo. El navegador envía el JWT en cada petición a la API.

Historias de usuario

  • RF01

    Como fanático quiero filtrar los calcetines por colección y talla para encontrar rápido uno de mi película favorita.

    Criterio de aceptación: Al elegir "Terror 80s" y talla 39-42 solo aparecen modelos de esa colección con esa talla, cada uno con foto, precio, stock y tallas.

  • RF02

    Como cliente quiero ajustar las cantidades del carrito y pagar para recibir un número de pedido.

    Criterio de aceptación: Al pagar con una tarjeta válida se muestra un resumen con un ID tipo SB-AAAAMMDD-XXXX y el stock baja. Si la tarjeta termina en 0000 el pago se rechaza y el stock no cambia.

  • RF03

    Como administrador quiero registrar un modelo nuevo asociado a una película o serie y actualizar su stock y precio.

    Criterio de aceptación: Sin un token con rol ADMIN el gateway responde 403. Con rol ADMIN el modelo aparece al tiro en el catálogo.

  • RF04

    Como usuario registrado quiero dejar de 1 a 5 estrellas y un comentario en la ficha de un producto.

    Criterio de aceptación: Sin sesión se pide ingresar. Con sesión la reseña se publica y el promedio de estrellas de la tarjeta se actualiza.

Decisiones y trade-offs

Sitio estático en GitHub Pages

Es gratis, se publica solo con cada cambio y carga rápido. A cambio, los datos del prototipo viven en el navegador (localStorage), así que cada visitante ve su propia copia del inventario y de los pedidos.

Un solo API Gateway

Centraliza la validación del JWT y los permisos, y las páginas no conocen los servicios. El costo es que pasa a ser un punto único de falla, por eso en la vista física hay dos réplicas detrás del balanceador.

Una base de datos por servicio

Separa los datos de seguridad de los del negocio y permite escalar cada parte por separado. Lo malo es que un reporte que cruce datos (por ejemplo, ventas por película) necesita consultar a varios servicios.

JWT firmado en el navegador

En el prototipo el token se firma con Web Crypto (HS256) para poder mostrar el flujo sin servidor, pero la clave queda visible en el JavaScript. En producción la firma la tiene que hacer AuthService en el servidor y la clave nunca debe llegar al cliente.
